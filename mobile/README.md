
# FieldOps Technician Mobile

React Native application built with Expo, TypeScript, and Expo Router. Android is the initial target, with iOS support retained.

## 1. Prerequisites

- Node.js 22 and npm.
- JDK 17 for local Android development.
- Android SDK and Android platform-tools.
- An Android emulator or Android device.
- Access to the FieldOps backend.
- An Expo/EAS account for cloud builds.

The project uses Expo Continuous Native Generation (CNG). Native Android and iOS project directories can be generated by Expo when required.

## 2. Configure the Environment

Install the dependencies:

```powershell
npm install
```

Create your local environment file:

```powershell
Copy-Item .env.example .env
```

Configure the API URLs in `.env`:

- `EXPO_PUBLIC_API_BASE_URL`
- `EXPO_PUBLIC_WS_BASE_URL`

Use the correct URLs for your development environment.

Do not commit `.env` or place private credentials and secrets in `EXPO_PUBLIC_*` variables. These variables are bundled into the mobile application.

## 3. Start Development

Start the Expo development server:

```powershell
npm start
```

Open the Android development target:

```powershell
npm run android
```

Open the iOS target where the required development tools are available:

```powershell
npm run ios
```

## 4. TypeScript and Tests

Run TypeScript validation:

```powershell
npm run typecheck
```

Run the project setup tests:

```powershell
npm test
```

The setup tests verify project configuration and required modules. They are not a replacement for end-to-end testing of authentication, job workflows, GPS, notifications, or offline synchronization.

## 5. Development Builds

The project uses Expo development builds and EAS Build to support native capabilities.

For an Android development build:

```powershell
npx eas-cli build --profile development --platform android
```

Start the bundler for a development client:

```powershell
npx expo start --dev-client
```

The EAS profiles are:

- `development` — internal development build.
- `preview` — internal preview build.
- `production` — production build configuration.

iOS native builds require suitable Apple development and signing configuration.

## 6. Location Requirements

The agreed FieldOps requirement is to track a technician while signed in, including when the application is in the background and while the technician is working on assigned jobs.

Tracking must stop on logout.

Background location depends on operating-system permissions, device settings, and platform restrictions. The application must handle denied or revoked permissions and location-service failures.

Expo location configuration alone does not implement the complete tracking workflow. Tracking lifecycle, update frequency, backend integration, battery usage, and device testing must be verified separately.

## 7. Backend and Security

The mobile application integrates with the existing FieldOps backend.

The backend remains authoritative for:

- Authentication and session validation.
- Tenant isolation and role-based access.
- Technician and job authorization.
- Job assignment and status transitions.
- Server-side validation and business rules.

The mobile client must handle expired sessions, network failures, permission errors, loading states, and unavailable services safely.

Never log authentication tokens, passwords, or unnecessary personal information.

## 8. Mobile Capability Scope

The planned technician application supports:

- Technician authentication and secure session storage.
- Assigned jobs and job details.
- Job status actions and history.
- Camera and job evidence capture.
- Push notifications.
- GPS tracking.
- Offline storage and synchronization.

Each capability must be validated against the actual backend contract and relevant mobile acceptance criteria.

## 9. Source Control and Packaging

Do not include these items in source archives:

- `.env`
- `node_modules/`
- `.expo/`
- Generated build outputs
- Private credentials or signing keys

Use `package-lock.json` to reproduce the dependency installation:

```powershell
npm install
```

Keep `.env.example` updated with configuration names only, never real secret values.
